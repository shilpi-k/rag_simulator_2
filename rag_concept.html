✂️ Step 2 — Chunking
PHASE 1: INDEXING — Split text into retrievable segments
Large documents can't be fed to an LLM all at once — context windows are limited. Chunking splits documents into smaller overlapping segments (~200–500 tokens each). The overlap ensures context isn't lost at boundaries. Each chunk becomes a retrievable unit.

Source text from Prior Auth Rules being split into chunks:

Prior authorization is required for all non-emergency specialist referrals and outpatient procedures above tier 2. The requesting provider must submit clinical documentation including diagnosis codes, treatment history, and medical necessity justification. Authorization decisions are made within 3 business days for standard requests and 24 hours for urgent cases. Appeals must be filed within 30 days of the denial notice and require additional supporting clinical evidence.

Resulting chunks stored for embedding:

CHUNK_001Prior authorization is required for all non-emergency specialist referrals and outpatient procedures above tier 2.
CHUNK_002The requesting provider must submit clinical documentation including diagnosis codes, treatment history, and medical necessity justification.
CHUNK_003Authorization decisions are made within 3 business days for standard requests and 24 hours for urgent cases.
CHUNK_004Appeals must be filed within 30 days of the denial notice and require additional supporting clinical evidence.

🔢 Step 3 — Embedding
PHASE 1: INDEXING — Convert text into numerical vectors
An embedding model (e.g. OpenAI Ada, Sentence-BERT) converts each text chunk into a high-dimensional numerical vector. Semantically similar texts produce vectors that are close together in vector space. This is what makes semantic search possible — not keyword matching, but meaning matching.

🗄️ Step 4 — Vector Database
PHASE 1: INDEXING — Store all embeddings for fast retrieval
All chunk embeddings are stored in a vector database (e.g. Pinecone, Weaviate, ChromaDB, pgvector). Unlike a traditional database that searches by exact match, a vector DB supports approximate nearest neighbor (ANN) search — finding the vectors most similar to a query vector in milliseconds across millions of entries.

❓ Step 5 — User Query
PHASE 2: RETRIEVAL — The query gets embedded too
When a user asks a question, the same embedding model converts the query into a vector. This is the key insight: by embedding both documents AND queries into the same vector space, we can find documents whose meaning is closest to the question — even if they don't share the same words.

Step 5 of 7
🔍 Step 6 — Similarity Search
PHASE 2: RETRIEVAL — Find top-k most relevant chunks
The query vector is compared against all stored vectors using cosine similarity (or dot product). The top-k chunks with the highest similarity scores are retrieved. These become the context that gets passed to the LLM. Only the most relevant knowledge is selected.

Query: "How long does prior authorization take?"

Top 2 chunks selected (similarity > 0.80). These will be injected as context into the LLM prompt.

Step 6 of 7
🤖 Step 7 — Augment & Generate
PHASE 3: GENERATION — Context + query → grounded response
The retrieved chunks are injected into the LLM prompt as context alongside the original query. The LLM generates a response grounded in this specific knowledge — not just its training data. This eliminates hallucinations for domain-specific questions and makes responses traceable to source documents.

Augmented prompt sent to LLM:

System instruction You are a helpful healthcare benefits assistant. Answer ONLY using the provided context. If the answer is not in the context, say so.
Retrieved context (top-2 chunks) [CHUNK_003] Authorization decisions are made within 3 business days for standard requests and 24 hours for urgent cases.
[CHUNK_002] The requesting provider must submit clinical documentation including diagnosis codes, treatment history, and medical necessity justification.
User query How long does prior authorization take?
